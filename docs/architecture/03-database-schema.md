# 03 — Database Schema

> **Implemented in Phase 2.** The authoritative definition is now the migration code in
> `whmcs/modules/addons/marketplace/migrations/`. This document describes intent. Where the
> two differ, the migrations win; §13 lists the deliberate differences from the Phase 1 draft.

## 1. Conventions

* Prefix: `mod_marketplace_` (WHMCS addon convention). It is omitted in the tables below for brevity.
* Engine InnoDB, charset `utf8mb4`, collation `utf8mb4_unicode_ci`. Slugs, codes and hashes use `ascii_bin` or `utf8mb4_bin` where exact matching matters.
* PK `id BIGINT UNSIGNED AUTO_INCREMENT`, unless noted. Public identifiers exposed in URLs and API are either slugs or `uuid CHAR(26)` ULIDs, never sequential IDs for sensitive objects (orders, licences, refunds, payouts, disputes).
* Timestamps are `DATETIME(6)` in **UTC**: `created_at`, `updated_at`. Soft delete uses `deleted_at` only where recovery is a requirement (products, reviews, coupons). **Financial and audit tables have no `updated_at` and are append-only.**
* Money is `DECIMAL(19,4)` + `currency_id INT UNSIGNED` (→ WHMCS `tblcurrencies.id`, no FK, ADR-005).
* Enumerations are `VARCHAR(32)` validated by PHP enums, not MySQL `ENUM`, so adding a state needs no table rebuild on large tables.
* JSON uses the schema builder's `json` type: native `JSON` on MySQL 8, and `LONGTEXT` with an automatic `CHECK (json_valid(col))` on MariaDB.
* WHMCS references (`client_id`, `user_id`, `admin_id`, `whmcs_*_id`) are `INT UNSIGNED` without FK (ADR-005). Integrity is kept by hooks and by the nightly `integrity:check` job.
* FKs between marketplace tables use `ON DELETE RESTRICT` by default. `CASCADE` is used only for pure child rows with no independent meaning (e.g. `product_tags`). Financial tables are **always RESTRICT**.
* Encrypted columns end with `_enc` (`BLOB`, sodium secretbox, 08 §4). Lookup of encrypted values uses a companion `_hash` column.
* Hashes (token, key, nonce, idempotency, ledger chain) are `CHAR(64)` hex in `ascii_bin`, not `BINARY(32)`. The Laravel 7 schema builder that WHMCS 8 bundles has no fixed-length binary type, and hex keeps values readable in admin tools. Wherever the tables below say `BINARY(n)`, read `CHAR(64)` hex.
* IP addresses are `VARCHAR(45)` text (IPv4/IPv6). Wherever the tables below say `VARBINARY(16)`, read `VARCHAR(45)`.
* Every index, unique, FK and CHECK name is generated by `IdentifierName`: `mkp_<table>_<columns>_<type>`, hashed down to fit MySQL's 64-character limit.

Legend: **PK** primary key, **UQ** unique, **IX** index, **FK** foreign key.

## 11. Migration plan (§57)

Migrations are PHP files returning a `Migration` instance, with `up()`, `down()` and
`tables()`. They use only Schema Builder features available since illuminate/database 7.x
(WHMCS 8 bundles 7.12). Raw SQL is used only for FULLTEXT and CHECK constraints and for
triggers. Behaviour of the `Migrator`:

* **Batches:** each run records its migrations in one batch, and rollback undoes whole batches, newest first.
* **Strict creation:** a migration refuses to start if any table it owns already exists without being recorded. It reports the table and changes nothing, rather than silently accepting an unknown schema or dropping data.
* **Failure cleanup:** MySQL DDL auto-commits, so a failed `up()` is cleaned up by calling that migration's `down()`. This is safe because of the strict-creation rule, and the failure is always re-thrown.
* **Locking:** `GET_LOCK('mod_marketplace_migrate')` serialises concurrent runs.
* **Cross-migration FKs:** FKs from an earlier table to a later one (e.g. `vendors.default_commission_rule_id`) are added by the later migration and dropped by its `down()`.

## 12. Scale notes (§38)

* Every list query is paginated. Large admin tables (orders, ledger, downloads, audit) use **keyset pagination** (`WHERE id < ? ORDER BY id DESC LIMIT n`), with offset pagination only for small result sets.
* Counters (views, downloads, sales, ratings) live in `*_stats` tables updated asynchronously, so hot catalogue rows are not write-locked by traffic.
* Catalogue listing reads only `search_index` (one table, covering indexes). Product cards are hydrated with a single `WHERE id IN (…)` batch for vendor names and media (no N+1).
* 1M+ orders: `order_items(vendor_id, created_at)` serves vendor dashboards, and aggregates come from `stats_daily`, never from live `SUM()` over the orders table.
* `downloads`, `license_events`, `audit_logs` and `webhook_deliveries` have retention settings and archive jobs. Partitioning is documented as an optional DBA step.

## 14. Database-enforced invariants

CHECK constraints are enforced by MySQL 8.0.16+ and MariaDB 10.2+:

* `product_license_tiers`: price ≥ 0 and sale price ≥ 0
* `order_items`: every amount ≥ 0
* `commissions`: commission + processing fee + tax withheld + vendor net = net, and vendor net ≥ 0 (the remainder rule, 04 §1)
* `wallets`: pending, reserved and paid totals ≥ 0 (available may go negative for vendor debt)
* `wallet_transactions`: amount > 0
* `payouts`: amount > 0, fee ≥ 0, net = amount − fee
* `commission_rules`: 0 ≤ percentage ≤ 100
* `coupons`: value ≥ 0, percentage ≤ 100
* `reviews`: rating 1–5
* `review_votes`: vote ∈ {−1, 1}

Append-only triggers (`AppendOnlyPolicy`):

| Level | Tables | Blocks |
|-------|--------|--------|
| Immutable | commissions, commission_adjustments, wallet_transactions, payout_events, refund_events, dispute_messages, domain_bids, audit_logs | UPDATE and DELETE |
| No update | downloads, license_events | UPDATE (retention jobs may DELETE old rows) |
